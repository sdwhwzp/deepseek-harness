# Agent Note: 内置 DeepSeek Harness 的桌面应用

Status: proposed

[English](2026-08-21-one-click-environment-launcher.md) | 中文

## 问题

面向普通客户的入口 `npx @deepseek-ai/dsh web` 假定机器已经安装兼容的 Node.js。从 checkout 运行还需要 Git、仓库固定的 pnpm 版本、依赖安装、完整构建和终端知识。如果客户的机器无法启动现有 Node CLI（命令行界面），位于该 CLI 内部的环境检测器也无法提供帮助。

仓库已经通过[不使用受管安装器运行源码](../../implemented/simplification/2026-08-10-source-run-without-managed-installer.zh.md)和[源码启动与仓库构建分离](../../implemented/simplification/2026-08-12-separate-source-launch-from-build.zh.md)，明确让源码用户负责 checkout 放置、Git 更新和产物新鲜度。面向客户的桌面产品不能只把这些贡献者职责变成图形化源码安装器，否则网络、提权、包管理器和编译器故障仍然是客户设置故障，只是换了一个界面。

客户需要的是一个具有独立窗口、桌面集成、经过测试的运行时和可预测生命周期的已安装应用。它必须在没有 Git、Node.js、pnpm、源码 checkout 或外部浏览器的情况下启动 DeepSeek Harness，同时保留现有 Web 体验和用户数据。

## 提案

### 产品与平台范围

在 `apps/desktop` 下增加一个私有 workspace 应用，包名为 `@deepseek-ai/dsh-desktop`。其发布产品包含 Electron、专用 Node 24 Harness 运行时、生产 Web 资产和全部运行时依赖。桌面应用属于产物发行形式，不是 npm 入口，也不是源码安装器。

首个版本支持：

- x64 架构的 Windows 10 和 Windows 11，提供 NSIS 安装器与便携式可执行文件。
- x64 架构的主流 glibc Linux 发行版，为 Debian 系统提供 deb 包，并在 Ubuntu、Debian、Fedora、openSUSE 和 Arch Linux 上验证 AppImage。
- 应用自有的简体中文与英文启动、失败、更新和关闭状态。加载后的 Harness Web UI 保持自身的语言行为。

macOS、ARM64、无图形界面的服务器、源码分支选择、客户提供的运行时包，以及常驻系统托盘模式不在首个版本范围内。

### 桌面进程模型

Electron 负责原生应用生命周期、一个 `BrowserWindow`、更新协调和一个内置 Harness 运行时子进程。主进程必须先取得当前用户的单实例锁，再创建子进程或窗口。第二次调用只聚焦现有窗口并退出。

Harness 子进程使用[单文件可执行 SDK 运行时发行](../../implemented/architecture/2026-07-10-single-file-executable-sdk-runtime-distribution.zh.md)已经验证的 `@yao-pkg/pkg --sea` 基础，构建为独立 Node 24 可执行文件。它通过桌面专用入口在 `127.0.0.1` 和操作系统分配的端口启动生产 Web profile，并且绝不打开默认浏览器。其封闭运行时载荷包含该 profile 所需的 Loader 组合、动态导入、原生模块、生产 Web manifest（元数据清单）和客户端资产。Electron 与运行时保持独立发布依赖闭包，因此 Electron 升级不能无提示地改变 Harness 的 Node 引擎或原生模块 ABI。

运行时通过专用父子控制通道报告带版本的 `ready` 或 `fatal` 消息。就绪消息只携带 loopback URL 和运行时版本。Electron 验证消息、要求 loopback 地址，并在加载 URL 前完成 HTTP 健康检查。运行时日志使用独立的有界流，因此日志行不能伪装成就绪消息。

关闭主窗口时，Electron 请求 Harness 正常 dispose（资源释放），等待运行时及其自有子进程树完全停稳，然后退出。安装更新采用同一关闭路径。有界关闭超时可以通过仓库的平台进程树提供方升级为强制终止，但桌面应用绝不能只依据持久化 PID 杀死进程。首个版本不会在窗口关闭后继续运行。

### 桌面窗口与启动体验

应用首先显示不依赖 Harness 服务器的内置启动文档。它展示 4 个有序状态：

1. 验证受支持的操作系统、x64 架构、打包资源 manifest 和可执行文件完整性。
2. 验证 Electron 数据目录和 `$DSH_HOME` 可写，但不改变现有内容。
3. 启动内置 Harness 运行时，并等待其结构化就绪消息与健康响应。
4. 在同一窗口内使用现有 Harness Web UI 替换启动文档。

每个状态均提供中英文标签、可访问的实时状态、有界且已脱敏的诊断，以及适用的重试或退出操作。运行时失败时继续保留内置启动文档，绝不能留下空白窗口或启动外部浏览器。内置资源损坏或缺失时要求重新安装已签名应用，而不是在启动期间下载可执行代码。

桌面应用保留现有 Web 凭据引导、设置、会话、工具和插件行为。Harness 数据继续使用 `$DSH_HOME`，包括默认的 `~/.dsh`，因此桌面应用与 CLI 运行共享同一份受支持数据。Electron 自有日志、更新状态和崩溃报告使用 Electron 的当前用户 `userData` 目录，并且绝不包含凭据值。

### Electron 与 loopback 安全

Harness 窗口启用 `contextIsolation` 和 Chromium 沙箱，并禁用 `nodeIntegration`。其 preload 只公开应用版本、平台、运行时状态、重试、退出、更新状态和确认安装更新所需的类型化桌面操作，不公开通用 IPC、子进程、shell、环境或文件系统原语。

主进程把导航和 API 流量限制为受信任运行时返回的准确随机 loopback origin。它拒绝非预期窗口、权限、下载、协议与导航；一个显式外部链接 allowlist 可以在操作系统浏览器中打开普通 HTTPS 文档。浏览器内容不能选择命令、可执行文件、工作目录或运行时 URL。

每次桌面运行都会生成不可预测的 bearer token，并通过私有控制通道传给受信任运行时，而不是通过 argv、URL 或持久化文件传递。Electron 请求层只为发往已验证 Harness origin 的 API 请求添加该 token，因此渲染器 JavaScript 无法读取它。桌面 Web 组合除了执行现有 Host、Origin、方法、内容类型和请求大小检查外，还要求该 token。普通 `dsh web` 组合保持当前浏览器信任行为。

内容安全策略只允许生产 Web 资源和应用所需的准确 loopback 连接。正式构建拒绝 Electron 开发工具、remote module 访问、非预期的未打包可执行文件、未经验证的运行时载荷，或未纳入已发布声明的依赖许可证清单。

### 打包、更新与发布所有权

`electron-builder` 从同一份已打 tag 的源码版本生成 Windows NSIS 安装器、Windows 便携式可执行文件、Linux AppImage 和 Linux deb 包。原生 runner 构建并冒烟测试自身平台产品。桌面产物内嵌每项运行时资源及其 SHA-256 值的 manifest；启动过程会在执行运行时前验证该 manifest。

应用在成功启动后检查已签名的发布元数据，并且不阻塞当前使用。它先报告版本与大小，再下载适用更新；验证签名与校验和后，请求客户确认重启并安装。NSIS 与 AppImage 产品可以在应用内完成替换；便携式可执行文件与 deb 包会下载已验证产品，并引导客户显式替换或安装软件包。任何产品都不会静默替换自身，无法访问更新服务也绝不能阻止已安装版本运行。

Windows 正式发布产物必须使用 Authenticode 签名。每个平台都发布不可变安装包、SHA-256 校验和、来源证明、软件物料清单和第三方声明。缺少必需签名、运行时 manifest 陈旧、Electron 与 Harness 版本不一致、打包入口未验证或干净机器冒烟测试失败时，发布流程必须拒绝发布。

### 文档所有权

桌面应用 README 负责记录受支持系统、安装包选择、数据与日志路径、启动与关闭行为、安全限制、更新行为、故障排除和移除方式。根文档与用户文档把桌面应用作为普通客户路径，同时为开发者和自动化保留 `npx`、已安装 CLI 与人工源码说明。英文和简体中文文档一起修改。

现有源码运行决策保持有效，因为桌面应用既不克隆或更新 checkout，也不安装开发工具链。桌面运行时只使用从已打 tag commit 构建的发布产物。

## 曾考虑的替代方案

**保留图形化源码安装器。** 它可以公开分支选择并重新构建当前源码，但会让 Git 主机、registry、包管理器、提权、磁盘容量和编译器行为成为每位客户首次运行的一部分。完整发布运行时会把这些问题转变为发布资格测试责任，而不是客户设置责任。

**只打包现有 CLI。** 独立 CLI 可以移除 Node 前置环境，但仍需要终端操作与外部浏览器进程所有权，无法提供所需的已安装桌面生命周期、窗口、更新交互或应用级安全限制。

**使用 Tauri 与 Node sidecar。** Tauri 可以缩小桌面壳体积，但会引入 Rust 和系统 WebView 差异，同时仍然需要完整 Node 运行时 sidecar。Electron 可以复用仓库的 TypeScript 专长，并在两个目标系统上提供一个经过验证的 Chromium 实现。

**在 Electron 主进程内运行 Harness。** 这会减少一个可执行文件，但 Harness 故障会同时终止原生生命周期，Electron 升级也会改变其 Node 引擎和原生模块 ABI。独立运行时具有显式就绪通道、独立故障隔离和两个平台一致的 Node 24 语义。

**通过 Electron 内嵌 Node 运行 Harness 子进程。** `ELECTRON_RUN_AS_NODE` 可以避免重复 Node，但会把原生依赖和受支持引擎行为耦合到 Electron 发布序列。已经验证的 SEA 打包基础接受更大的安装体积，以换取单独验证的 Harness 运行时。

**保留外部浏览器而不是 `BrowserWindow`。** 这种方式体积更小，并且已经由 `dsh web` 支持，但不具备已安装桌面应用的行为，也无法强制实施相同的导航、权限、token 注入、更新或关闭即停止生命周期。

**关闭窗口后继续在系统托盘运行。** 后台运行可以缩短重新打开时间，但会降低进程所有权和资源使用的可见性。首个版本选择显式关闭即停止行为；后续托盘模式需要单独可见的用户设置与生命周期设计。

## 验收标准

- 客户可以在干净机器上安装或运行适用的已签名 Windows 或 Linux x64 产品，无需 Git、Node.js、pnpm、源码 checkout 或终端即可在桌面窗口中到达现有 Harness Web UI。
- 启动过程会分别拒绝不受支持的平台、错误架构、损坏或缺失的打包资源、不可写数据目录、格式错误的就绪消息、非 loopback 运行时 URL、失败的健康响应，以及就绪前退出的运行时。
- 成功启动不会执行包管理器操作、权限提升、源码下载、分支选择、依赖安装或客户机器构建。
- 应用提供双语、键盘可访问的启动、失败、重试、更新和关闭状态。快照覆盖两种语言及每个实质性应用自有状态。
- Harness Web UI 针对共享 `$DSH_HOME` 保留凭据引导、设置、会话持久化和普通工具行为，不会在 Electron 日志或更新状态中暴露凭据。
- 安全测试证明渲染器内容无法访问 Node API、通用 IPC、bearer token、任意导航、权限、下载、外部协议、命令、文件系统路径或非 Harness loopback origin。
- Loopback API 测试拒绝缺失或错误的桌面 token，以及无效 Host、Origin、方法、内容类型或正文大小；普通 `dsh web` 保留现有信任行为。
- 重复执行应用会聚焦现有窗口，并且不会启动另一个运行时。关闭窗口、选择退出、安装更新或处理正常操作系统终止后，不会留下自有 Harness 或后代进程。
- 运行时崩溃后保留内置错误 UI 和有界脱敏诊断。重试只启动一个新运行时；它不能通过陈旧状态或 PID 重用采用或终止无关进程。
- 原生 CI 生成并冒烟测试 NSIS 安装器、便携式可执行文件、AppImage 和 deb 包。发布资格测试覆盖干净的 Windows 10 和 Windows 11 x64 系统，以及未安装开发工具的已声明 Linux 发行版矩阵。
- 更新测试覆盖每种产品受支持更新路径中的有效、不可用、中断、损坏、未签名、错误版本和客户拒绝场景。每个未安装结果发生后，当前应用仍然可用。
- 聚焦单元与集成测试、双语桌面快照、打包运行时冒烟测试、类型检查、lint、文档同步、网站链接验证、依赖声明和空白校验全部通过。

## 风险

Electron 加专用 Node 运行时的安装体积会显著大于浏览器启动器或 Tauri 壳。发布必须公布体积测量结果，并让 Electron、Harness、重复原生组件和 Web 资产保持可分别审计的依赖闭包；不能只为缩小体积就把 Harness 耦合到 Electron 的 Node ABI。

桌面应用会让 loopback Web 服务器成为本地安装应用安全边界的一部分。Bearer token 泄漏、宽松导航、渲染器 Node 访问、薄弱的内容安全策略、伪造就绪消息或不完整的进程清理，都可能暴露 Harness 功能或凭据。Token 传递、请求注入、`BrowserWindow` 限制、结构化就绪和完整子进程 dispose 是发布阻断行为。

发行完整运行时会把依赖和编译器故障移出客户设置流程，但也会让每项发布产物具有平台针对性。每个受支持平台都必须一起重新构建并验证 Electron、Node、原生 addon、打包 Web 依赖闭包、安装器、签名、更新元数据、来源证明和干净机器测试。

AppImage 与 deb 安装的 Linux 桌面集成和自更新行为不同。应用必须说明适用的更新路径，不能声称每种软件包都能自行替换。企业代理、签名或执行策略可能阻止更新下载或运行时执行；已安装版本必须保持可用，并报告准确的受阻操作。

共享 `$DSH_HOME` 可以保持 CLI 互操作性，但也会允许桌面应用与 CLI 进程争用同一份受支持数据。现有持久化锁和损坏行为仍然有效；桌面应用必须呈现这些故障，不能创造第二种数据迁移，也不能静默复制凭据。
