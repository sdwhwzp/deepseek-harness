# Agent Note: 把发起委派那一步的归属带进工作流的子代理

Status: implemented

[English](2026-09-09-delegated-turn-ownership.md) | 中文

## Problem

工作流脚本把工作分发给子代理。每个子代理运行在自己的会话里，其轮次不记录任何认证归属：派生路径从未收到归属，`turn/start` 也就无从写入。

本分支按轮次记录的归属来归集用量、按账号额度与会话可见性。因此被委派的轮次不计入任何人的账，也对发起它的操作者隐藏；而同样的工作若直接在父会话里执行，则正常计费、正常显示。在暴露该问题的部署上，一次分析把 48 次模型调用中的 42 次委派了出去，于是可见开销只有真实开销的八分之一，操作者自己的会话也从列表里消失。

委派工具本就把 `exec.principal` 传给了 `subagents.start`，只有工作流引擎这条路径遗漏了。`SubagentStartRequest.principal` 早已存在，文档也写明它会持久化到子代理的提示上——所以缺口是一个字段没有跨三个包传下去，而不是缺少能力。

## Decision

`WorkflowStartRequest` 增加可选的 `principal`。工作流工具从 `exec.principal` 填入，worker-thread 引擎在整个运行期间持有它，该运行发出的每次 `subagents.start` 都带上它。若运行本身没有归属（非 agent 调用方），其子代理保持无归属，而不是替它编一个。

## Alternatives considered

**把归属记进子会话头。** 否决：会话头属于已发布格式、按精确成员集校验，新增成员即格式变更，需要迁移边并会被旧读取方拒绝——对于一个提示本就携带的字段而言过重。

**读取时按 `parentSession` 解析归属。** 保留，但作为账目补救而非修复：[dsh-spend 正是这么做的](https://github.com/sdwhwzp/dsh-spend)，使已经无归属落盘的历史仍能正确计费。它帮不了直接读会话日志的消费方，而且一份记录了"谁跑了这一轮"的日志，胜过让每个读取方各自推导。

## Consequences

被委派的轮次现在与发起委派的那一步归属相同，因此计费、额度与会话可见性对待工作流的方式，与它所替代的工作一致。

只有此后启动的轮次才会记录。已经写入的会话在日志里仍无归属；需要其归属的消费方可沿委派链解析。

## Testing

`workflow-worker-thread.spec.ts` 断言：两个子代理的脚本中，两个子代理都收到该运行的归属；而未带归属启动的运行，其子代理保持无归属而不是被猜测填充。
